Getting started

Indium programs are plain UTF-8 text files ending in .in. The interpreter reads your file, checks it, and executes its statements.

1. Make the command available

On Windows, build Indium once and run install-windows.cmd, or use the standalone Install-Indium.cmd with your existing build. The installer copies the runtime into a permanent per-user folder and adds its bin folder to your user PATH. Close all terminal windows and open a new terminal after installation.

indium --version

The default build reports indium 0.1.0-alpha.1 (OpenGL + audio). A build made with --no-default-features reports (terminal-only) instead. See Windows installation for build requirements and the installer's exact behavior. You do not need Rust every time you run a program.

On a compatible Linux machine, the release ZIP's indium-linux launcher can run the included runtime directly. From the project's main folder:

./indium-linux run examples/hello.in

That launcher is for Linux, not Windows. The README contains the Linux/macOS source-build instructions and system requirements.

2. Create a program

Create a folder for your programs, open a text editor, and save this as program.in:

print("Hello, Indium!")

Choose UTF-8 text encoding without a byte-order mark (BOM). In Windows Notepad's Save As dialog, choose All files so it does not quietly save program.in.txt. Showing file extensions in File Explorer makes this easier to spot.

Open a terminal in that folder. One way on Windows is to open the folder in File Explorer, click the address bar, type powershell, and press Enter.

indium run program.in

Expected output:

Hello, Indium!

The command does not create an .exe for this program. It executes the .in source through the installed interpreter.

3. Understand the two kinds of paths

The path in the terminal command starts from your terminal's current folder. For example, from the main project folder:

indium run .\examples\hello.in

From inside examples, use this instead:

indium run .\hello.in

PATH lets the terminal find the Indium executable. It does not search for your program file. You can also give an absolute program path:

indium run "C:\Users\v\My Programs\program.in"

Paths inside Indium source start from that source file's folder. If games/demo.in calls renderer.image("assets/player.png", ...), Indium looks for games/assets/player.png, regardless of your terminal's current folder. Local imports follow the same rule. An imported function uses its own defining file's folder for its file and asset operations.

Inside an Indium string, use forward slashes in Windows paths or escape each backslash: "C:/Users/v/data.txt" or "C:\\Users\\v\\data.txt".

4. Add values and a function

Replace the contents of your file with:

name = "flight"
score: integer = 0

fn award(points: integer) -> integer {
    return points * 2
}

for round in 1..4 {
    score += award(round)
}

if score >= 10 {
    print(name, "scored", score)
} else {
    print("Keep going!")
}

This prints flight scored 12. 1..4 produces 1, 2, and 3; the end is excluded. score: integer declares a type. += updates the existing value. The function returns twice its argument, and the if branch checks a boolean condition.

Newlines separate statements. Braces group blocks. Indentation makes the code readable, but does not define the blocks. You do not need let, var, a main function, or a semicolon at the end of each line.

5. Read input and arguments

Terminal input reads one line as text:

name = trim(input("Your name: "))
print("Hello, " + name + "!")

For arguments supplied when launching a program:

values = args()
print("Number of arguments:", len(values))
for value in values {
    print(value)
}

Save that program as arguments.in, then:

indium run arguments.in -- hello "two words"

args() returns ["hello", "two words"] as a list of text values. The -- separates interpreter flags from arguments for your program.

6. Check a file without running it

indium check program.in

This parses the program and checks names, known types, control flow, and local imports. It does not execute print, write files, open a window, or make HTTP requests. Some information is only known at runtime, so a successful check does not prove every operation will succeed.

If a program fails, read its first error message. It includes the file, line, column, and usually the source line with a caret. A missing file and a type mismatch are different problems; Troubleshooting explains the common messages.

7. Explore the included demos

From the project's main folder, after installing the command:

indium run examples\hello.in
indium run examples\collections.in
indium run examples\results.in
indium run examples\closures.in
indium run examples\2d.in

Run each command separately. The 2D demo stays open until you close its window or press Escape. Its controls are arrow keys for speed, Space for sound, and F11 for fullscreen. The filesystem, audio, interactive, and HTTP demos have side effects described in the handbook's example index.

Continue with the Language chapter, or jump to Graphics, input, and audio to make a window.

Language reference

This chapter describes the implemented language. For a first program, read Getting started. For function signatures, use the Standard library.

Indium source files use UTF-8 and the .in extension. Newlines separate statements. Semicolons are optional separators when placing statements on one line. Blocks use braces. Comments use //, #, or nested /* ... */. Save UTF-8 without a BOM.

Modes

mode = terminal
// Other implemented modes: background, 2d

Terminal is the default. 2d creates an OpenGL-backed window after top-level initialization. background creates no graphics window, but does not detach the process or suppress an inherited console. Set the mode before the scheduler starts.

Variables and values

count = 49
speed = 2.5
name = "Indium"
ready = true
missing = none
score: integer = 0
position: decimal = 0
anything: any = 49
anything = "can change type"

A variable's first assignment defines it in the current lexical scope. Reassignment updates the nearest existing binding. Otherwise, the assignment creates a new local binding. Each block and function introduces a scope.

Annotation Values it accepts Typical value
integer Signed 64-bit whole numbers 49
decimal Finite floating-point numbers; integer assignments widen 2.5
text Immutable Unicode text "hello"
boolean Exactly true or false true
list Lists and this implementation's lazy ranges [1, 2]
map Maps; local module values also use this coarse runtime category {name: "Indium"}
function User functions and built-in function values A function name
none Only the absence value none
any Any value Use for intentionally changing types

These are the complete annotation names. There are no generics such as list<integer>, nullable-type syntax, or separate result/module annotations. Lists/maps do not enforce an element/field schema. Several special runtime values use the coarse any category internally; type_of provides extra names such as "result" and "module". A built-in namespace and a local module are different internal value kinds, so do not rely on them sharing a type_of name.

Inferred variable types remain fixed. A decimal binding accepts an integer by widening it; an integer binding does not silently accept decimals or text. An any annotation explicitly allows varying types. Function parameters can be annotated or inferred from each call. An unannotated function's return values may have different types across calls.

For a value that starts absent and is filled in later, declare it any:

selected: any = none
selected = "first item"
print(selected)

Without the annotation, a variable initialized with none can only hold none. any(value) is an identity conversion; it does not change a variable's declared type. A typed parameter accepts the same assignment rules as a typed variable. An unannotated parameter gets its runtime binding type from that call's value; use parameter: any if its type must change within the function.

Integers are signed 64-bit. Overflow raises an error. Decimals are finite 64-bit floating-point values. Division always produces a decimal; division by zero, non-finite results, and invalid mathematical domains raise errors. Numeric comparison between an integer and a decimal can lose integer precision; keep large integers as integers. Integer/integer equality and ordering remain exact; integer/decimal equality checks avoid rounding a large integer into a false match.

Numeric literals may contain digit-separating underscores (1_000_000) and decimal exponents (1.25e-3). Use 0.5, not .5, and 2.0, not 2..

An integer result stays integer for integer +, -, *, %, and valid integer **. Mixing a decimal into numeric arithmetic produces a decimal. / always produces a decimal, even for two integers. Decimal arithmetic has ordinary floating-point rounding; 0.1 + 0.2 should not be used as an exact decimal-money representation. There is no arbitrary-precision or fixed-point numeric type.

Text accepts single or double quotes. Escapes: \n, \r, \t, \0, \\, \", \'. Text literals cannot span physical lines. Indexing and length count Unicode scalar values, not bytes or grapheme clusters.

For example, len("äλ") is 2 and "äλ"[-1] is "λ". A visible character made from multiple combining scalars can have a length greater than 1. There is no raw-string prefix, string interpolation, triple-quoted literal, or \u escape; write Unicode characters directly in the UTF-8 source. Join strings with + and text(value), or print separate values with print.

Operators

From tighter to looser binding:

  1. Calls, member access, indexing.
  2. ** exponentiation (right associative).
  3. Unary +, unary -.
  4. *, /, %.
  5. +, -.
  6. .. (end-exclusive integer range).
  7. <, <=, >, >=, is.
  8. ==, !=.
  9. not / !.
  10. and / &&.
  11. or / ||.

not and ! negate the following comparison, so not x is integer means not (x is integer). Conditions and logical operators require booleans; Indium does not implicitly treat numbers, lists, or text as true/false. Logical operators short-circuit. Use a < b and b < c rather than chained comparisons. Compound assignments: +=, -=, *=, /=, %=.

Text concatenates with text using +. Lists concatenate with lists. Use text(value) when explicitly building text; print accepts values directly. Ranges iterate upwards and exclude the end. A range whose start exceeds its end is empty.

print(2 + 3 * 4)        // 14
print(2 ** 3 ** 2)      // 512: 2 ** (3 ** 2)
print(-2 ** 2)          // -4: -(2 ** 2)
print(5 / 2)            // 2.5
print(7 % 3)            // 1
print(decimal(2) ** -1) // 0.5
print(not 49 is text)   // true

For integer base ** exponent, the exponent must be an integer from 0 through 4294967295, and the result must fit in 64 bits. Use a decimal base for negative or fractional powers. math.pow is another decimal-power option after importing math. There is no **= assignment, integer-division operator, bitwise operator, increment/decrement operator, ternary operator, or expression-form if.

Compound assignment requires an already-existing target. count += 1 does not declare count. An indexed/member assignment target is evaluated once before its right-hand side, so side effects in an index are not repeated.

== and != can compare unlike types and return false/true as appropriate; numeric integer/decimal equality is the special numeric case described above. Ordering supports numbers and text with text. Text ordering is lexical, not locale-aware alphabetical sorting. Functions compare by identity, not by body.

Logical operators require booleans on both evaluated sides. They do not return an arbitrary operand as a shortcut value. false and dangerous() and true or dangerous() do not call dangerous.

Type and state checks

print(49 is integer)
print("hello" is text)
print(none is none)

answer = success(49)
if answer is success {
    print(answer.value)
}
problem = error("something failed")
if problem is error {
    print(problem.error)
}

is checks a type, none, or a result variant. == compares values. They are not interchangeable. Applying is success to a non-result value is an error. Only the matching .value or .error result field can be read; .ok is always a boolean. Result constructors and functions returning results are ordinary values, not a general exception-handling system.

There is no automatic result unwrapping, try/catch, throw, or ? operator. User functions can return results too:

fn divide(a, b) {
    if b == 0 {
        return error("cannot divide by zero")
    }
    return success(a / b)
}

answer = divide(12, 3)
if answer.ok {
    print(answer.value) // 4
} else {
    print(answer.error)
}

success(value) and error(value) each take exactly one value. The payload can be any value, not just text. Use is success/is error or .ok before reading the matching field. value is any is always true; none is none tests absence. is is not an object-identity operator, and value is "hello" is invalid.

Collections

items = [1, 2, "three"]
point = (10, 20) // parentheses with commas also form a list
player = {name: "flight", score: 0}
items[0] = 49
player.score += 10
player["active"] = true
push(items, 240)
print(items[-1], len(items), player.name)

Lists and maps are mutable reference values; assigning a collection to another variable aliases it. Elements can contain different types. Map keys are text; record.field is shorthand for record["field"]. Map iteration visits keys in sorted order. Invalid indexes and missing keys raise errors. A negative index counts from the end. Text is immutable. items.length and name.length also report length.

Lists/maps compare structurally, with a bounded depth for cyclic structures. Printing deeply nested/cyclic structures truncates after eight levels.

List and text indexes start at zero. -1 is the last item, -2 the previous item. Reading or assigning outside the existing list bounds fails; assignment does not append. Use push to append and pop to remove the last item. There are no slicing, list-comprehension, .push(), or direct text-mutation methods.

{} and [] create empty collections. Map literal keys may be bare names or quoted text, but cannot be arbitrary key expressions. Use indexed assignment for a computed key. Duplicate keys in a map literal are rejected. Updating an existing key replaces its value; assigning a new text key adds it. A map does not preserve insertion order and has no key-deletion API yet.

items = [10, 20]
alias = items
alias[0] = 49
copy = items + []
copy[0] = 99
print(items[0], copy[0]) // 49 99

player = {}
field = "score"
player[field] = 240
print(player.score)    // 240
print(contains(player, "missing")) // false

List concatenation creates a new outer list, but nested lists/maps remain shared references: it is a shallow copy, not a deep clone. contains tests a map key's presence before you access a possibly missing field. Map iteration and keys(map) visit sorted text keys.

start..end creates a lazy ascending range of integers. It can be iterated and passed to len.

Functions and control flow

ready = true
count = 3

fn add(a, b) {
    return a + b
}

fn double(n: integer) -> integer {
    return n * 2
}

if ready {
    print(double(49))
} else if count > 10 {
    print("more than ten")
} else {
    print("waiting")
}

for n in 0..10 {
    if n == 3 { continue }
    if n == 8 { break }
    print(n)
}

while count > 0 {
    count -= 1
}

loop {
    break
}

Functions are visible throughout their enclosing block, so mutual recursion works. Variable initialization still occurs in source order. Calling a function before a captured variable has been initialized produces a runtime diagnostic. Functions are first-class values and retain lexical captures. A function without a return statement returns none. break and continue apply only to the current function's loops.

For-loops snapshot a list/map's iteration values at loop entry. Mutating the original collection does not change the iteration sequence. Ranges are lazy.

for accepts ranges, lists, text, or maps. Text iteration gives one-scalar text values; map iteration gives keys, so fetch a value with map[key]. There is no two-variable key/value loop syntax. Each loop iteration has a fresh block scope.

An assignment to an existing outer name updates that binding, even inside an if or function. A type annotation does not force a fresh shadowing binding. Function parameters and for iteration variables create their own bindings.

total = 0
if true {
    total += 5
    temporary = "only inside this block"
}
print(total) // 5
// Accessing temporary here would fail: it is out of scope.

There is no let/var/const declaration syntax. Built-in bindings, imported aliases, and declared function names are read-only; normal variables are mutable. Use a different name rather than trying to overwrite a built-in such as print.

Functions as values and closures

Pass a function by writing its name without parentheses. Add parentheses to call it. User functions require exactly the declared number of positional arguments. They have no optional, variadic, default, or named parameters.

The function annotation accepts actual user/built-in function values. Some other kinds of value are also callable, including conversion types, input, audio, and result constructors, but are not in that runtime type category. Use any for a parameter meant to accept those general callable values.

fn twice(value: integer) -> integer {
    return value * 2
}

fn apply(operation: function, value) {
    return operation(value)
}

chosen = twice
print(apply(chosen, 21)) // 42

A function can declare and return another named function. It retains access to the environment where it was created, even after the outer function returns:

fn make_counter() {
    value = 0
    fn next() {
        value += 1
        return value
    }
    return next
}

counter = make_counter()
another = make_counter()
print(counter(), counter(), another()) // 1 2 1

These are lexical closures. There are no anonymous/lambda function expressions yet. A function name is available throughout its enclosing block, which allows forward calls and mutual recursion. Captured variables still need to have been initialized before the call uses them. Recursive algorithms must respect the runtime's depth limits.

return ends the function immediately, including from nested loops. Bare return and falling off the end return none; an annotated non-none return type will reject that value. There is no implicit return of the final expression. return at top level or directly inside a recurring handler is invalid.

Imports

import math
import files as fs
import game
import "modules/geometry.in" as geometry

Built-in modules: math, files, net, time, game, text. Window, rendering, input, and audio APIs are available without imports. text also remains a conversion/type name; its text helpers are accessible as members, with or without import text.

Local module paths are relative to the importing source file. Their extension must be .in. Without an alias, the filename stem is used. Imports are checked recursively, loaded once, and cached by canonical path. Circular imports are reported. Import errors preserve the failing file and source position.

A module exports its own declarations except names starting with _. Built-in names inherited by a module are not re-exported. Module fields can be read; mutating module state should happen through its exported functions. A module function's file and asset paths remain relative to the defining module.

Use as to choose a convenient alias or fix a filename that is not a valid identifier. Without an alias, a local file's stem is used, with hyphens changed to underscores. Local modules are not found by a package search path; use an explicit relative or absolute .in path.

All local imports are loaded and checked before execution, including imports inside functions or a branch that would not run. A module's top-level statements execute when its import actually runs, once per canonical file path. Reimporting the same file under another alias shares its state rather than creating a copy.

Local module fields cannot be directly rebound with module.score = 10. Exported functions can update their captured module variables. Exported collections are reference values, so mutating an exported list/map affects the shared collection. Names starting with _ are inaccessible through exports, not a general security boundary around the file's behavior.

See examples/imports.in and examples/modules/geometry.in for a runnable two-file program. Use simple filenames and keep modules in a project folder alongside their assets.

Recurring execution

mode = 2d
import game
import time
game.tps = 240
fn update() {}

every frame {
    renderer.clear("black")
} loop

every tick {
    update()
} loop

every 5 seconds {
    print("Ping")
} loop

Handlers must be declared at module level after the variables they use. The trailing loop token is required. Timers also accept second, milliseconds, and millisecond. An interval expression is evaluated once at registration.

All top-level initialization finishes before the scheduler begins. Tick, frame, and timer handlers share the language's normal lexical scopes. Statements inside a handler run in a fresh block scope each invocation; assignments to existing outer variables persist.

Simulation uses an accumulator and game.dt = 1 / game.tps. Render timing uses time.dt. Rendering FPS does not set simulation TPS. The scheduler sleeps until the next relevant deadline instead of waiting for a render frame before considering ticks. A blocking render, HTTP call, sleep, or long handler can still delay work because the runtime is single-threaded.

game.max_catchup defaults to 8 ticks per scheduler iteration. Missed tick time beyond that bound is discarded and counted in game.dropped_ticks; it is not replayed in an unbounded catch-up loop. Raise the bound for high TPS with very low FPS. An overdue timer fires once and advances to its next scheduled interval, skipping missed invocations. This keeps its cadence without bursts.

Call stop(), game.stop(), or window.close() to finish. Closing the native window also exits. A terminal/background program with handlers remains alive until stopped; one without handlers finishes after its statements run.

See Ticks, frames, and timers for the lifecycle, exact counters, overload behavior, timer interval limits, and a complete stopped timer example.

Names, layout, and syntax boundaries

Identifiers are case-sensitive. They start with _ or a Unicode alphabetic character, followed by alphabetic/numeric characters or _. score and Score are different names. Avoid reserved words and built-in names for your variables.

Control words are fn, if, else, while, for, in, loop, break, continue, return, import, as, every, and is. true, false, none, mode names, and success/error also have special language meaning. and/or/not are operators. Tick/frame and time-unit words are interpreted in their handler context.

Lists, maps, calls, and parameter lists support comma-separated multiline layout and trailing commas. Parentheses containing a comma form a list: (49,) is a one-item list, (49) groups a value, and () is not an empty-list literal. Use [] for an empty list.

Keep binary operators with the expression they continue, for example end a continued line with +. A newline that is not consumed by a larger expression separates statements. There is no backslash line-continuation syntax.

Some familiar-looking forms are intentionally absent: assignment is a statement rather than an expression; = does not test equality; in belongs to a for loop rather than a membership expression; and there is no match, switch, do/while, elif, class, or struct statement.

Implementation limits

  • Interpreted execution; no native compilation yet.
  • Syntax nesting/chains are limited to 128, local import depth to 64.
  • At most 32 nested execution blocks/function calls and 64 simultaneous expression evaluations; either guard may trigger first. There is no tail-call optimization.
  • --max-steps N optionally bounds execution; normal runs have no instruction budget. --frames N bounds rendered frames for graphics smoke tests.
  • Names and known scalar types are checked before execution; dynamic module, collection, and callable values receive further checks at runtime.
  • Closures and cyclic collections use reference counting, without a tracing collector. Reference cycles can retain memory for the life of the process.
  • No user-defined structs/classes/enums, named/default arguments, destructuring, exception syntax, async language features, or package installation yet.

Standard-library reference

Unless stated otherwise, invalid argument types/counts produce source-location diagnostics. none is the normal return value for actions without a value. All filesystem and asset paths resolve relative to the executing source file.

? marks an optional positional argument in the signatures below. It is reference notation, not syntax. A return value of none means an action completed without producing data. Runtime diagnostics abort execution; explicit success(...)/error(...) results are ordinary values your code can inspect.

What needs an import

Names How to access them
General helpers, scalar conversions, collection/text helpers, success, error Already available
window, renderer, input, audio Already available; media support is part of the default build
math, files, net, time, game Import the namespace first, for example import math
text helper namespace Available through text; import text is also accepted

An alias such as import files as fs uses the same APIs as the original name. Properties use module.name; functions add parentheses. For example, time.elapsed is a property and time.now() is a function.

Terminal and general helpers

API Returns Behavior
print(values...) none Format any number of values, separated by spaces, followed by a newline
write(values...) none Same spacing, without the final newline; output is flushed
input(prompt?) / input.read(prompt?) text Optionally format/print one prompt, then read one line without its line ending
type_of(value) text Return the runtime type name
assert(condition, message?) none Require a boolean; a false condition raises the provided formatted message or Assertion failed
args() list Text arguments provided after the CLI -- separator
stop() none End execution normally; takes no exit-code argument
sleep(seconds) none Block the runtime thread for a number of seconds in 0..86400

print() emits a blank line. write() with no arguments emits nothing. Lists, maps, results, and other values are printed in a human-readable representation, not serialized JSON. Printing a decimal can look like an integer (1.0 prints as 1); use type_of or is decimal to inspect its type.

input accepts zero or one prompt value; prompts need not be text because they are formatted. An empty line returns "". End-of-input also yields empty text, so a loop should not assume it will always receive another nonempty answer. Input failures are diagnostics. input.read is terminal input, distinct from the same namespace's keyboard/mouse functions.

print("Score:", 49)
write("No newline yet. ")
print("Now there is one.")
assert(49 > 0, "Score must be positive")
print(type_of(49), type_of(49.0)) // integer decimal

integer(decimal) truncates toward zero and checks the signed 64-bit bounds. Numeric text conversions trim surrounding whitespace. Invalid conversions raise a diagnostic; they do not return an error result. list() and map() with no arguments are invalid: use [] and {} to create empty collections.

print(integer(" 22 "), integer(-2.9), integer(true)) // 22 -2 1
print(decimal("2.5"), boolean("false"))             // 2.5 false
result = success({answer: 49})

failure = error("not found")

Result properties are .ok (always boolean), .value (successful payload only), and .error (failed payload only). Wrong-state field access raises a diagnostic. Type annotations have no separate result name; a function can return a result without annotating its return, or use -> any.

HTTP — import net

net.get(url) and net.post(url, body) use the installed curl program through argument-based process spawning, without a shell. HTTP(S) only, 15-second timeout, 16 MiB response cap, normal TLS validation, and no automatic redirects.

On transport success, the result contains {status: integer, body: text}. HTTP error status codes such as 404 are still transport successes; inspect .status. Missing curl, TLS/network failures, oversized or non-UTF-8 responses return an error result. Calls block the runtime thread. The initial POST helper sends curl's default form content type.

The exact functions are net.get(url: text) and net.post(url: text, body: text). They return success/error results. A success payload has .status (integer) and .body (text). A URL with a non-HTTP(S) scheme is rejected as an argument diagnostic.

On Windows the runtime launches curl.exe; a PowerShell alias named curl does not substitute for that executable. You can check it with curl.exe --version. On other systems the executable name is curl.

import net
response = net.get("https://example.com")
if response is error {
    print("Transport failed:", response.error)
} else {
    status = response.value.status
    if status >= 200 and status < 300 {
        print(response.value.body)
    } else {
        print("HTTP status:", status)
    }
}

Executing this block accesses the network. It is only checked, not called, by the documentation verifier. HTTP(S) support does not include a web server, websockets, custom headers, cookies/session management APIs, streaming downloads, file-upload helpers, automatic redirects, or a general JSON library.

Graphics, input, and audio

The default Indium build includes OpenGL-backed 2D rendering, keyboard/mouse input, and OGG/WAV audio. window, renderer, input, and audio are available without imports. A terminal-only build cannot use the media backend.

Your first window

Save this as drawing.in:

mode = 2d
window.title = "My first Indium window"
window.width = 640
window.height = 400
window.vsync = false

every frame {
    renderer.clear("#141724")
    renderer.rect(40, 70, 160, 90, "indium")
    renderer.circle(360, 120, 45, "#58d6a7")
    renderer.line(40, 230, 500, 230, "white")
    renderer.text("Hello, Indium!", 40, 280, 28, "white")
} loop

Run it with indium run drawing.in. The window stays open until closed. The three-frame limit shown in the documentation test marker is only a verifier setting; it is not part of the program's runtime behavior.

Top-level code configures the window. It opens after initialization finishes. Draw inside every frame, after that point. The runtime presents the completed frame automatically; there is no user-callable present function.

Use one renderer.clear at the beginning of each frame. Drawing order matters: later shapes and images are drawn over earlier ones. There is no built-in scene graph, sprite object, camera transform, layer system, or collision engine.

Coordinates, shapes, and colors

The origin (0, 0) is the top-left. X increases to the right and Y downwards. Rectangles/images use a top-left corner plus width and height. A circle's X/Y position is its center. Lines use two endpoint positions.

Coordinates accept integers or decimals and are converted to integer pixels by truncation toward zero. Allowed coordinates are -1000000 through 1000000. Widths, heights, and circle radii accept numeric values in 1..16384, then are truncated. Keep positive sizes even when a shape is partly offscreen.

Colors accept:

Form Example Meaning
RGB hex text "#7163ff" Opaque red/green/blue channels
RGBA hex text "#7163ff80" RGB plus alpha at the end
RGB list [113, 99, 255] Three integer channels, each 0..255
RGBA list [113, 99, 255, 128] Three channels plus alpha, each 0..255
Named color "white" black, white, red, green, blue, or indium

Alpha 0 is transparent and 255 is opaque. Omitted optional drawing colors are white. Named colors are lowercase. indium currently means #7163ff; it is a temporary convenience color rather than a finalized brand palette.

renderer.rect is filled, renderer.outline is a one-pixel rectangle border, renderer.line is one pixel wide, and renderer.circle draws a filled circle. There are no rotation, gradients, stroke-width, polygon, or shader APIs yet.

Text and images

Fragments to place inside a frame handler:

renderer.text("Default size is 24", 20, 20)
renderer.text("Larger text", 20, 60, 36, "#ffffff")
renderer.image("assets/player.png", 20, 130)
renderer.image("assets/player.png", 100, 130, 64, 64)

Text uses the embedded DejaVu Sans font. It supports Unicode text within that font's glyph coverage; no custom-font loader is exposed. Font size accepts a number from 1 through 256. To set a text color, supply the size first, followed by the color. Text runs are limited to 16384 UTF-8 bytes and a raster size of 16384 by 4096 pixels. An empty text run draws nothing.

Images support PNG, JPEG, and BMP, including source alpha where the format supports it. The three-argument image call uses the original dimensions. The five-argument form scales to the requested width/height. There is no four-argument form, source-rectangle cropping, image tint parameter, or rotation. Decoded source images are limited to 8192 by 8192 and a 128 MiB decode allocation.

All asset paths are relative to the .in file containing the call (or the function's defining file). Use the supplied examples/assets/checker.png when trying the existing examples/2d.in; the player.png fragment above assumes you supply that file yourself.

Decoded images are cached by canonical path. Replacing the file during a run does not automatically reload the cached image. Text rasters are cached by text and size, with a small cache that clears after 128 entries. Avoid repeatedly drawing huge images or constantly generating large unique text strings.

Screenshots

Movement with a fixed tick

mode = 2d
import game
import math
window.title = "Move with arrows"
window.width = 640
window.height = 400
window.fps = 60
window.vsync = false
game.tps = 240
x = 100.0
y = 100.0
speed = 180.0

every tick {
    if input.key_down("left") { x -= speed * game.dt }
    if input.key_down("right") { x += speed * game.dt }
    if input.key_down("up") { y -= speed * game.dt }
    if input.key_down("down") { y += speed * game.dt }
    x = math.clamp(x, 0, window.width - 30)
    y = math.clamp(y, 0, window.height - 30)
    if input.key_pressed("F11") { window.toggle_fullscreen() }
    if input.key_pressed("escape") { stop() }
} loop

every frame {
    renderer.clear("#141724")
    renderer.rect(x, y, 30, 30, "indium")
    renderer.text("Arrows move; F11 fullscreen; Escape quits", 12, 12, 18)
} loop

The speed is pixels per second. game.dt turns it into pixels per simulation tick. X and Y start as decimals because movement produces decimal values. The frame handler only draws the latest state. See Scheduling for the difference between game.dt and the render delta time.dt.

Window settings and fullscreen

window.title, .width, .height, .fps, .vsync, .fullscreen, and .exclusive can be configured before opening and changed while running. window.backend is read-only. It is "not initialized" before a normal media window opens and "opengl" afterward; terminal-only builds report "unavailable".

To start in borderless fullscreen, set window.fullscreen = true at top level. The default window.exclusive = false uses desktop fullscreen. For exclusive fullscreen, set .exclusive = true as well; the platform can reject it. There is no monitor selector, display-mode selector, or refresh-rate selector yet.

window.toggle_fullscreen() flips the fullscreen setting. Toggling from an existing window preserves the prior windowed size for restoration. Native resize events update the reported window dimensions. Borderless fullscreen uses the display size. Width/height configuration is mainly meaningful in windowed mode.

window.fps is a software render cap. VSync may cap it further, and a slow machine may achieve less. For a high requested FPS or uncapped rendering, disable VSync explicitly if appropriate. Even then, nothing guarantees the requested rate. The backend explicitly requests OpenGL; it does not switch to SDL's software renderer when OpenGL fails.

Playing sound

The shortest call is audio("sound.ogg"). The equivalent explicit call is audio.play("sound.ogg"). Both return a positive integer handle for one voice.

// Assumes assets/music.ogg exists beside this program's assets folder.
music = audio.play("assets/music.ogg", 0.5, true)
audio.pause(music)
audio.resume(music)
audio.volume(music, 0.25)
print(audio.playing(music))
audio.stop(music)

The optional arguments are volume (default 1.0, range 0..1) and looping (default false). They are positional. Looping requires the third argument, so include a volume value even if you want the default volume.

Pause/resume/stop/volume return a boolean indicating whether a live handle was found. audio.playing(handle) returns false for paused, finished, or stopped voices. audio.volume sets the volume; it is not a getter. Reusing a file starts a separate voice, so effects can overlap. At most 128 voices coexist, including paused voices. The mixer clamps combined output into the stereo sample range.

Audio supports OGG with Vorbis and PCM WAV, with mono or stereo source audio. The runtime resamples to the opened device's rate and mixes stereo output.

Files are decoded once and cached by canonical path. Each decoded sound is limited to 256 MiB. Sound devices open lazily on the first playback call, including in terminal/background programs. File, codec, or device failures are runtime diagnostics rather than result values.

Keep a terminal sound alive

When a terminal script ends, its audio stops too. The supplied examples/audio.in uses brief sleeps to demonstrate playback before exiting. Another approach is a timer that keeps the program alive until the sound finishes. Do not block a 2D handler with a sleep to wait for music; let the scheduler continue.

There is no audio.stop() with no arguments to stop all voices. Call audio.stop(handle) for a particular sound. The global stop() function exits the entire program.

Ticks, frames, and timers

Indium can execute a normal terminal script, keep a timer-driven program alive, or run a 2D window with independent simulation and rendering rates. All Indium handlers execute on the same runtime thread.

Program lifecycle

  1. The loader reads, parses, and checks the entry file and local import graph.
  2. Top-level statements run in order. They initialize variables, import modules, configure the window, and register recurring handlers.
  3. If stop() was called during initialization, execution ends immediately.
  4. Otherwise, 2d mode opens the window; terminal/background mode opens none.
  5. The scheduler runs registered ticks/timers and, for 2D, graphical frames.

A terminal/background file without handlers finishes after its statements run. A 2D program keeps polling its window even if no handlers were registered. An endless top-level loop prevents initialization from finishing, so a 2D window will never open. Put ongoing work in recurring handlers instead.

Functions are hoisted within their scope, but variables initialize in source order. Declare a handler's captured variables before declaring that handler. Handlers must be at module level, outside functions, loops, conditions, or other handlers. Imported modules may also declare module-level handlers.

Three handler forms

Form Trigger Typical work
every tick { ... } loop Fixed simulation step Movement, physics, game rules
every frame { ... } loop Render deadline, in 2D mode Clear and draw the next frame
every 500 milliseconds { ... } loop Recurring real-time interval Status messages, periodic updates

The trailing loop is required in every form. second/seconds and millisecond/milliseconds are accepted. There is no every minute form; write every 60 seconds instead.

count = 0

every 10 milliseconds {
    count += 1
    print("Timer:", count)
    if count == 3 {
        stop()
    }
} loop

This prints three timer messages, then exits. The interval expression is evaluated once when the handler is registered. Changing the variable used to calculate it later does not change the registered interval. Supported intervals are 0.000001 seconds through 365 days; actual precision depends on the runtime and operating system. A one-microsecond request is not a real-time guarantee.

Each invocation gets a fresh block scope. Variables created only inside that block do not persist to the next invocation. Assign to an existing outer variable, such as count, to retain state.

break and continue apply to an actual for, while, or loop inside the handler. They cannot terminate the recurring registration itself. Use stop() to finish the program.

Simulation TPS and fixed delta time

import game
game.tps = 100
position = 0.0

every tick {
    position += 50 * game.dt
    if game.ticks == 3 {
        print("Three ticks completed.")
        stop()
    }
} loop

game.tps means ticks per second. Its default is 240, and it accepts numeric values from 1 through 10000. game.dt is the fixed duration of the current tick in seconds: 1 / game.tps. Multiplying a speed in pixels/second by this delta makes a movement update express a distance per tick.

The scheduler increments game.ticks before running that tick's handlers. Ticks are only dispatched when at least one tick handler exists; simply importing game does not start a simulation counter.

Rendering FPS and frame delta time

window.fps requests a maximum render frequency: default 60, or 0 for uncapped. time.dt is the actual monotonic time between frame starts, not 1 / fps. window.vsync can further restrict presentation to the monitor/driver cadence.

Rendering FPS does not determine TPS. A 240-TPS simulation can request 60, 144, or another rendering FPS. These are requested schedules, not performance guarantees. There is no automatic interpolation between previous/current tick states in this release; a frame draws whatever state your handlers have produced.

game.frames counts completed frame iterations. It is zero while the first frame's handlers run. time.dt starts at 0 before scheduling and can be very small on the first frame. It is a render value, so do not use it as a timer or fixed-tick delta in a terminal-only program.

time.now() and time.elapsed both report monotonic elapsed seconds. During top-level initialization they measure from interpreter creation. The start instant is reset just before the scheduler loop; a timestamp taken during initialization is therefore not a persistent wall-clock timestamp. No calendar date, time zone, or system-clock API is exposed yet.

What happens during one scheduler pass

Order Action
1 Poll window events in 2D mode
2 Accumulate elapsed time and dispatch due simulation ticks
3 Dispatch due timers
4 If a frame is due, run frame handlers and present it
5 Sleep until the nearest relevant deadline, subject to a small polling cap

Multiple handlers in the same phase run in registration order. All handlers for one frame draw onto the same backbuffer, which is presented after they finish. If multiple handlers clear it, later clears erase earlier drawing.

Keyboard/mouse press edges have separate tick and frame buffers. A press is visible to all handlers in the next tick and all handlers in the next frame; it is then cleared for that phase. Several catch-up ticks do not each see a new press. See Graphics, input, and audio.

Catch-up, overload, and missed timers

If the runtime falls behind, the simulation can process several ticks in one scheduler pass. game.max_catchup defaults to 8, accepts integer values from 1 through 1000, and bounds that burst of work. Excess due tick intervals are discarded and counted in game.dropped_ticks.

An overdue timer fires once, then advances its next deadline to the next point on its original cadence. It skips missed invocations rather than replaying all of them in a burst.

Increasing the catch-up limit can help preserve tick counts under a blocking renderer, but does not make slow handler code faster. Very large bursts can also delay rendering and input processing. Measure the program and reduce blocking or expensive work before relying on extreme limits.

Blocking and stopping

sleep, terminal input, filesystem work, HTTP requests, and drawing execute synchronously on the runtime thread. A long call delays ticks, timers, and frames. sleep is useful in a simple terminal audio demo; using it to pace a 2D handler blocks the entire runtime.

The audio callback mixes playback on its internal device thread after a sound has been started. This does not make Indium handler code multithreaded.

stop(), game.stop(), and window.close() end the whole program normally. Closing the native window also ends it. A tick/frame/timer handler that calls one of these should not rely on later statements running: the interpreter checks the stop state between statements.

For short graphics tests, use indium run drawing.in --frames 3. To bound interpreter work, use --max-steps; neither option is a general wall-clock timeout. See the CLI reference.

Flag Meaning

--frames N End the scheduler after N graphical frame iterations

Recipes

These patterns use the current language and built-in library. Code blocks marked run are complete examples with no interactive input or external network requests. File-writing examples say what they create.

Count occurrences with a map

words = split(lower("red blue red green blue red"), " ")
counts = {}
for word in words {
    if contains(counts, word) {
        counts[word] += 1
    } else {
        counts[word] = 1
    }
}
for word in counts {
    print(word, counts[word])
}

The output order is blue 2, green 1, red 3, because maps iterate sorted keys. Reading a missing key would fail, so the code checks contains first. This example splits on a literal space; real text with punctuation or multiple whitespace kinds needs your own normalization/tokenization rules.

Filter and reverse a list

values = [5, 12, 3, 18, 9]
large = []
for value in values {
    if value >= 10 { push(large, value) }
}

reversed = []
for offset in 0..len(large) {
    push(reversed, large[-1 - offset])
}
print(large)    // [12, 18]
print(reversed) // [18, 12]

This creates new outer lists. There is no built-in filter/reverse API, slicing, or list comprehension yet. Iterating a list uses a snapshot of its elements, so adding items to the original does not extend an already-running for loop.

Sort a small numeric list

fn sorted_copy(values: list) -> list {
    result = values + []
    count = len(result)
    for pass in 0..count {
        for index in 0..(count - 1) {
            if result[index] > result[index + 1] {
                previous = result[index]
                result[index] = result[index + 1]
                result[index + 1] = previous
            }
        }
    }
    return result
}

original = [9, 2, 7, 1]
print(sorted_copy(original)) // [1, 2, 7, 9]
print(original)              // [9, 2, 7, 1]

This simple bubble-sort example is for small lists of mutually comparable numbers. It is quadratic work, not a fast standard-library sort. values + [] makes a shallow copy so swapping outer elements does not modify the original.

Keep state in a returned function

fn make_counter(start: integer) -> function {
    value = start
    fn increment() -> integer {
        value += 1
        return value
    }
    return increment
}

next_score = make_counter(48)
print(next_score(), next_score()) // 49 50

The inner function keeps its captured value alive. Separate calls to make_counter create independent environments. examples/closures.in shows the same idea with two counters. Reference cycles are not reclaimed by a tracing collector yet, so avoid manufacturing many cyclic long-lived graphs.

Return a recoverable error

fn positive(value: integer) {
    if value <= 0 { return error("must be positive") }
    return success(value)
}

for number in [-2, 49] {
    checked = positive(number)
    if checked is success {
        print("Accepted:", checked.value)
    } else {
        print("Rejected:", checked.error)
    }
}

Results let your caller handle a failed operation without a runtime diagnostic. error("message") constructs a result; it does not throw an exception. Conversion, bounds, and most media errors are still diagnostics, so returning a result from your own function does not automatically catch those failures.

Read and save a text note

This example creates a notes directory beside its .in file and appends to notes/log.txt when executed. The documentation verifier only checks it.

import files
created = files.mkdir("notes")
if created is error {
    print("Could not create notes folder:", created.error)
    stop()
}

saved = files.append("notes/log.txt", "Another Indium run.\n")
if saved is error {
    print("Could not append:", saved.error)
    stop()
}

loaded = files.read("notes/log.txt")
if loaded is success {
    print(loaded.value)
} else {
    print("Could not read:", loaded.error)
}

Use files.write to replace the complete contents instead of appending. Read and inspect the operation's result even when files.exists returned true; existence is not a promise that access will succeed.

Run a repeated task a fixed number of times

remaining = 3
every 10 milliseconds {
    print("Remaining:", remaining)
    remaining -= 1
    if remaining == 0 { stop() }
} loop

Declare remaining outside the handler so each invocation updates persistent state. stop() exits the entire program. To keep other handlers running after one task is finished, keep a boolean flag and have that handler do nothing when the flag is false; there is no unregister API yet.

Validate interactive numeric input

See examples/guessing-game.in. Its parse_guess function:

  1. Trims the input text.
  2. Rejects empty text or more than three characters.
  3. Checks every character against "0123456789".
  4. Converts to integer only after those checks.
  5. Rejects values outside 1..100 and returns a success/error result.

This avoids trying to recover from integer("not a number"), which raises a diagnostic rather than returning a result. The three-character bound also keeps the conversion far below the 64-bit integer limit. The game expects interactive input; interrupt it with Ctrl+C if you want to leave before the game ends.

Troubleshooting

Start with the first complete error, including its filename and line number. An installation error happens before a program runs; a language diagnostic refers to your .in source; an error result is data returned to your program.

The terminal cannot find indium

If the message says indium is not recognized, the terminal cannot find the executable through its PATH. This does not indicate a syntax problem in your program. Run the Windows installer, close all terminal windows, and open a new terminal. Existing terminal host processes may retain their old environment. If necessary, sign out of Windows and sign back in.

Verify with indium --version before trying a source file. For a direct check of a source build, run this from the main project folder containing Cargo.toml:

.\target\release\indium.exe --version

That relative path is wrong from C:\Users\v or from inside examples. If there is no target\release\indium.exe in the project, the Windows build has not completed. Installing Rust alone does not build or install Indium.

The source file cannot be found

Your terminal's current folder determines the path in indium run .... From the project root, use examples\hello.in; from inside examples, use hello.in. Quote paths containing spaces. Check that an editor did not add .txt after the .in extension. The CLI expects lowercase .in.

If the first character produces an unexpected-character error, check the text encoding. Save UTF-8 without BOM.

Once the source starts, file/import/asset paths inside the program are relative to its defining .in file, not to the terminal's folder. Keep the demo assets and local modules in the supplied folder structure.

Windows build and DLL problems

Message Meaning and next step
cargo is not recognized Rust/Cargo is missing from this terminal; install Rust or reopen the terminal after installing it
Microsoft linker/build tools are missing Install the MSVC C++ toolchain, including Desktop development with C++
SDL2.lib was not found in an x64 folder Use the SDL2 Visual C++ development package and point the helper at its extracted folder

The original build helper incorrectly put literal quotes in RUSTFLAGS. The updated script uses CARGO_ENCODED_RUSTFLAGS to preserve paths with spaces. Download the updated project if you still have the original helper. Do not delete your working Windows build just to replace documentation files.

The release ZIP's prebuilt Linux runtime is not a Windows executable. The standalone Windows setup installs an already-built Windows runtime; it does not compile one or download a replacement in the background.

Unknown variable or read-only name

Define a variable before using it, check spelling/capitalization, and consider scope. A variable created inside a block is not visible outside that block. Function declarations are hoisted, but captured variables still initialize in source order. Handler state should be declared before the handler.

Built-ins and imports have read-only bindings. Use a different variable name instead of assigning to print, input, text, math, or another imported alias. A declared function name cannot be reassigned either.

Expected integer, got decimal

The first assignment normally fixes a variable's runtime type. Division always produces a decimal, and functions such as math.floor also return decimals.

Deliberately invalid example:

count = 10
count = count / 2

Use a decimal binding if fractions are part of the program:

count = 10.0
count = count / 2
print(count)

Or explicitly convert a result with integer(...) when truncation is intended. Use name: any = ... only when changing types is intentional. Applying any(value) alone does not change a variable's declared type.

Conditions require booleans

This fails because a number is not a boolean:

if 1 { print("not reached") }

Write if count > 0, if len(items) > 0, or an explicit boolean condition. boolean(1) is not a truthiness conversion. Also use == for equality; is is for a type, none, or a result state.

Result has the other state

You accessed .value on an error, or .error on a success:

result = error("not found")
print(result.value)

Check result is success, result is error, or result.ok first. Do not apply is error to an arbitrary integer/text value: state checks require a result. An invalid conversion or media operation is usually a diagnostic, not a result that can be caught with this pattern. See the standard-library return types.

List/map access fails

Lists/text use integer indexes starting at zero. -1 is the last item. Maps use text keys. Index assignment does not extend a list. Reading a missing map key fails; use contains(map, key) first. Text is immutable.

items = [49]
print(items[1])

Use push(items, value) to append. A range is lazy and cannot be indexed even though its coarse runtime type is list. There is no items[1:3] slice syntax.

The window never opens or drawing fails

Set mode = 2d before scheduling. Let top-level initialization finish: a top-level infinite loop prevents the runtime from opening its window. Put ongoing logic in every tick/every frame handlers.

Drawing during initialization fails:

mode = 2d
renderer.clear("black")

Move drawing into every frame { ... } loop. Input polling also requires the initialized window, so put it in handlers. every frame without mode = 2d is an error. A terminal-only executable must be rebuilt with default features to gain graphics/audio support.

An OpenGL/window creation failure may be a display, SDL, or driver problem. Check the backend message. The implementation explicitly requests OpenGL and does not silently switch to SDL's software renderer. mode = 3d is recognized but deliberately reports that it is not implemented.

Shapes, text, images, or input look wrong

Clear once at the beginning of each frame, then draw in the order you want. Later drawing covers earlier drawing. Check X/Y positions and positive sizes. Color channels must be integer 0..255, and color names are lowercase.

For colored text, use renderer.text("label", x, y, 24, "red"). Passing the color as the fourth argument puts text where a numeric font size belongs. renderer.image takes either 3 or 5 arguments. Use PNG/JPEG/BMP and verify the source-relative asset path. Cached images do not automatically reload when a file changes during the same run.

Use key_down for held movement and key_pressed for a one-time action. Focus loss clears input state. Tick/frame edge buffers are separate, but several catch-up ticks do not each count as a new press.

There is no sound

Check that the build includes media, the file is OGG/Vorbis or PCM WAV, the path is correct, the sound is mono/stereo, volume is above zero, and the playback device opens.

A terminal program that ends immediately also stops its sound immediately. Use a short sleep in a terminal demo or keep a scheduler running. A paused voice reports audio.playing(handle) == false; that is expected. Completed handles also report false. There is no audio.stop() with zero arguments.

Dummy-device testing verifies state/decoding but produces no audible sound. If the SDL_AUDIODRIVER=dummy test environment variable is set on your own machine, remove it before testing speakers.

Simulation or timers seem slow

TPS/FPS are requested rates rather than guaranteed throughput. Handlers execute on one thread. sleep, terminal input, HTTP, large file work, and heavy drawing delay other work. Use game.dt for fixed-tick movement and time.dt only when you intentionally want the last render-frame duration.

Inspect game.dropped_ticks if the catch-up limit is discarding due ticks. Timers skip missed invocations rather than firing every overdue occurrence. See Scheduling. --frames does not bound terminal-only timers; use a stop condition or --max-steps as appropriate.

A feature or familiar syntax is missing

This release has no native .in compilation, package downloads, 3D, classes, structs, exceptions, async syntax, slicing, string interpolation, or JSON helper. indium build/indium install report explicit unfinished-feature messages. The handbook overview separates current capabilities from plans. Prefer an implemented recipe to a guessed API that only resembles another language.

Implementation map

main.rs handles CLI arguments and file loading. loader.rs canonicalizes paths, loads/checks the local import graph, detects cycles, and retains source text for runtime diagnostics. It never executes programs during check.

lexer.rs produces UTF-8-aware tokens with byte offsets and line/column spans. parser.rs uses a Pratt expression parser and structured statement parser. ast.rs defines the syntax tree, basic type vocabulary, and recurring events.

checker.rs checks lexical names, known scalar types, annotations, function arity, scope rules, and control-flow placement. It hoists function declarations and checks their bodies after the enclosing declarations. Dynamic values remain runtime-checked; the pass is intentionally not described as a complete static type inference system.

interpreter.rs executes the AST. It implements lexical closures, functions, control flow, checked arithmetic, indexed assignment, module caching, and source error stacks. Assignment targets are evaluated once before the right-hand side. The runtime uses reference-counted lexical environments and collection values. It has instruction, nesting, evaluation, and call guards rather than relying on host stack overflows or raw Rust panics for normal program errors.

runtime/scheduler.rs drives independent tick and render deadlines, with bounded catch-up and timer cadence. Handlers share lexical state and run on one thread. The fixed-step accumulator is also tested independently from wall-clock time.

stdlib exposes built-ins and modules through a consistent value/call interface. File/HTTP operational failures use explicit success/error results. Networking launches curl with individual arguments.

media/backend.rs uses rust-sdl2 to create an actual OpenGL renderer. CPU-decoded images and font rasters are cached; GPU resources created for a draw are scoped and freed. The SDL offscreen resize path rebuilds its pbuffer-backed window; native desktop drivers preserve their context on resize.

media/audio.rs uses Symphonia to decode OGG/Vorbis and PCM WAV into cached audio clips. An SDL audio callback mixes voices with per-voice gain, pause/loop state, and linear sample-rate conversion. Audio uses an internal callback thread while language code runs on the runtime thread; shared mixer state is protected by a mutex. The device is opened only on demand and paused before destruction.

Deliberate boundaries

  • This is its own language implementation, not translation into a host language for execution, and not a collection of hard-coded example programs.
  • No fake native build command, package installer, 3D renderer, or AI API.
  • No browser playground, external website, or separate game editor.
  • No project GitHub changes or remote pushes in this development session.
  • The source snapshot uses system SDL2 rather than requiring three SDL extension libraries. Image, font, and audio codec work uses Rust crates.

Rust library entry points

The project is both a CLI binary and a Rust library crate. src/lib.rs exports the lexer, parser, checker, loader, interpreter, runtime, media, and standard library modules. These are pre-alpha implementation APIs, not a stable embedding contract.

The convenience helper indium::run_source(source) checks a source string, executes it, captures normal terminal output, and returns Result<String>. It sets a one-million-step execution budget. It is used throughout the language tests:

let output = indium::run_source("print(49)\n").unwrap();
assert_eq!(output, "49\n");

Local file imports need a real defining file path, so run_source rejects programs containing them. For file-backed execution, use loader::compile_file(Path::new("program.in")), create an interpreter::Interpreter with that program and interpreter::Options, and call its run() method. The options control output capture and step/frame limits. The loader's compile_file name means parsing/checking into this interpreter's program representation; it does not generate machine code.

Diagnostics retain source spans, filenames, messages, and call notes. render can combine one with source text to produce the same kind of caret display the CLI uses. Error results produced by Indium programs are separate language values, not Rust loader/interpreter diagnostics.

Edit the Markdown files in docs/ and keep examples aligned with the current implementation. Interactive, filesystem-writing, and public-network snippets are not run automatically; the new interactive game gets controlled test input separately.
